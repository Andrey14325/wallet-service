# wallet-service

Мини-платёжный сервис на Go: кошельки, пополнение, переводы между кошельками, история операций и выписка с бегущим балансом. Все изменения денег проходят в транзакциях PostgreSQL и фиксируются в журнале операций (ledger).

Проект учебный, но сделан так, как делают настоящие платёжные сервисы: деньги в целых числах, блокировки строк без дедлоков, идемпотентные переводы, фоновая сверка баланса с журналом.

## Возможности

- создание кошелька и получение баланса
- пополнение кошелька
- перевод между кошельками с `Idempotency-Key`
- история операций кошелька с keyset-пагинацией
- выписка: последние операции и баланс после каждой из них
- фоновая сверка: баланс каждого кошелька должен совпадать с суммой его записей в журнале

## Стек

- Go, стандартный `net/http` (маршруты вида `POST /accounts/{id}/deposit`)
- PostgreSQL 16, драйвер `pgx` и пул `pgxpool`
- миграции: `golang-migrate`
- Docker и Docker Compose (многоэтапная сборка, запуск от непривилегированного пользователя)
- логирование через `log/slog` в формате JSON

## Быстрый старт

Нужен только Docker.

1. Создайте в корне проекта файл `.env`:

   ```
   POSTGRES_USER=wallet
   POSTGRES_PASSWORD=wallet
   POSTGRES_DB=wallet
   ```

2. Запустите всё одной командой:

   ```bash
   docker compose up -d --build
   ```

   Compose поднимет базу, дождётся её готовности, применит миграции и только потом запустит приложение на порту `8080`.

3. Проверьте:

   ```bash
   curl -X POST http://localhost:8080/accounts \
     -H "Content-Type: application/json" \
     -d '{"user_id":"alice"}'
   ```

Остановить: `docker compose down` (данные сохранятся в volume), `docker compose down -v` (вместе с данными).


## API

Все тела запросов и ответов в JSON. Суммы везде в копейках. Ошибки возвращаются в виде `{"error": "..."}`.

| Метод и путь | Описание | Успех |
|---|---|---|
| `POST /accounts` | создать кошелёк, тело: `{"user_id": "..."}` | `201` и кошелёк |
| `GET /accounts/{id}` | получить кошелёк и баланс | `200` |
| `POST /accounts/{id}/deposit` | пополнить, тело: `{"amount": 1000}` | `200`, `{"status":"ok"}` |
| `POST /transfers` | перевод, заголовок `Idempotency-Key` (UUID) | `200`, `{"status":"ok"}` |
| `GET /accounts/{id}/history` | история операций, параметры `limit`, `cursor` | `200` |
| `GET /accounts/{id}/statement` | выписка с балансом после каждой операции, параметр `limit` | `200` |

Тело перевода:

```json
{ "from_account_id": "<uuid>", "to_account_id": "<uuid>", "amount": 300 }
```

### Коды ошибок

| Код | Когда |
|---|---|
| `400` | неверный id, сумма, лимит, курсор или `Idempotency-Key`; перевод самому себе |
| `404` | кошелёк не найден |
| `409` | `Idempotency-Key` уже использован для другого перевода |
| `422` | недостаточно средств |
| `500` | внутренняя ошибка (подробности только в логе) |

### Примеры

Пополнение и перевод:

```bash
curl -X POST http://localhost:8080/accounts/<id>/deposit \
  -H "Content-Type: application/json" -d '{"amount":1000}'

curl -X POST http://localhost:8080/transfers \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1c0b9e-3f6a-4a56-9c58-0d9f4f1c2a11" \
  -d '{"from_account_id":"<from>","to_account_id":"<to>","amount":300}'
```

В PowerShell используйте `curl.exe` вместо `curl` (в нём `curl` это псевдоним другой команды).

История, страницами по две записи:

```bash
curl "http://localhost:8080/accounts/<id>/history?limit=2"
# в ответе: {"items":[...], "next_cursor":"eyJ..."}
curl "http://localhost:8080/accounts/<id>/history?limit=2&cursor=eyJ..."
```

Когда страницы закончились, поля `next_cursor` в ответе нет.

Выписка (новые операции сверху):

```bash
curl "http://localhost:8080/accounts/<id>/statement?limit=10"
```

```json
{ "items": [
  { "amount": -100, "balance_after": 700, "...": "..." },
  { "amount": 1000, "balance_after": 1000, "...": "..." }
] }
```

## Архитектура

```
cmd/                 точка входа (main)
cmd/loadtest/        нагрузочный тест переводов
internal/
  config/            флаги и переменные окружения
  handlers/          HTTP: разбор запроса, коды ответов, middleware
  service/           бизнес-правила и валидация
  storage/           SQL и транзакции (pgx)
  models/            структуры и общие ошибки
  reconciler/        фоновая сверка баланса с журналом
  server/            http.Server, маршруты, graceful shutdown
migrations/          SQL-миграции
```

Слои: `handlers` → `service` → `storage`. Каждый слой объявляет интерфейс того, что ему нужно от нижнего, поэтому service легко тестировать с подставным хранилищем. Ошибки (`ErrValidation`, `ErrAccountNotFound`, ...) живут в `models`, а handler превращает их в HTTP-коды через `errors.Is`.

Для каждого запроса работают три middleware: идентификатор запроса (заголовок `X-Request-ID`), логирование (метод, путь, статус, время) и перехват паник.

## Ключевые решения

**Деньги.** Хранятся в `BIGINT` в копейках, никаких `float`. На уровне базы стоит `CHECK (balance >= 0)`.

**Журнал.** Каждое изменение баланса порождает запись в `ledger_entries`: пополнение даёт одну строку, перевод две (списание и зачисление с одним `operation_id`). Главный инвариант: баланс кошелька равен сумме его записей в журнале. Изменение баланса и запись в журнал всегда выполняются в одной транзакции.

**Конкурентные переводы.** Перевод блокирует обе строки кошельков через `SELECT ... FOR UPDATE`, затем проверяет баланс, списывает, зачисляет и пишет две строки в журнал. Чтобы встречные переводы A→B и B→A не вызывали дедлок (`40P01` в Postgres), строки всегда блокируются в одном порядке, по id.

**Идемпотентность.** Клиент присылает `Idempotency-Key`, он используется как `operation_id`. Повтор того же перевода возвращает успех и не меняет баланс. Повторное использование ключа с другими параметрами даёт `409`. Дополнительно журнал защищён уникальным ограничением `(operation_id, account_id)`.

**Пагинация.** История использует keyset-пагинацию по `(created_at, id)`, а не `OFFSET`: `OFFSET` заставляет базу читать и выбрасывать все пропущенные строки, и чем дальше страница, тем она медленнее. Курсор это пара `(created_at, id)` последней отданной записи, закодированная в base64. Чтобы узнать, есть ли следующая страница, запрашивается на одну запись больше.

**Индекс для истории.** Миграция 3 создаёт индекс `(account_id, created_at DESC, id DESC)`. Замер через `EXPLAIN ANALYZE` на таблице в миллион строк (100 кошельков по 10 000 записей): без индекса `Parallel Seq Scan` и около 40 мс, с индексом `Index Scan` без сортировки и около 0,06 мс.

**Выписка.** Баланс после каждой операции считается оконной функцией: `SUM(amount) OVER (ORDER BY created_at, id)`.

**Фоновая сверка.** Горутина по таймеру проходит по кошелькам пачками (keyset по `account_id`), одним запросом читает баланс и сумму журнала и пишет в лог `balance mismatch`, если они разошлись.

**Остановка.** Сервер и сверка останавливаются по `SIGINT`/`SIGTERM`: HTTP-сервер завершается через `Shutdown` с запасным `Close`.

**Docker.** Многоэтапная сборка: компиляция в образе с Go, запуск в минимальном `alpine` от обычного пользователя без прав администратора. Файл `.env` в образ не попадает (`.dockerignore`).

## Тесты и проверка под нагрузкой

Тестовое покрытие частичное. Есть юнит-тесты на `AccountService` (валидация, ошибки хранилища, пополнение, перевод) с подставным хранилищем:

```bash
go test ./...
```

Для остальных частей тестов нет: `LedgerService` (история и выписка), handlers, storage и сверка не покрыты. Их стоило бы дописать, в первую очередь логику пагинации в `LedgerService` и интеграционные тесты на настоящей базе, но в рамках учебного проекта они не написаны. Вместо них поведение проверялось вручную (запросы к API, SQL-проверка инварианта баланса и журнала, `EXPLAIN ANALYZE`) и нагрузочным тестом.

Нагрузочный тест (нужна запущенная база с применёнными миграциями):

```bash
go run ./cmd/loadtest
```

Он создаёт два кошелька и запускает 400 параллельных переводов по одной копейке в обе стороны. Результат: все переводы успешны, дедлоков нет, общая сумма денег не меняется.

## Ограничения и что можно улучшить

- Нет аутентификации: любой клиент может работать с любым кошельком.
- Выписка считает бегущую сумму по всем записям кошелька, поэтому на очень больших кошельках она дорогая. В реальных системах баланс после операции хранят прямо в записи журнала.
- Два одновременных запроса с одним ключом, но разными кошельками, не гарантированно блокируют друг друга. Полная защита требует отдельной таблицы ключей идемпотентности с уникальным ключом.
- У пополнения нет клиентского ключа идемпотентности: идентификатор операции генерирует сервер.
- Тестов мало: покрыт только `AccountService` (см. раздел выше). Нет тестов на `LedgerService`, handlers и storage, нет интеграционных тестов на настоящей базе и CI.
